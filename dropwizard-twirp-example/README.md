# dropwizard-twirp-example

A minimal, runnable Dropwizard 5 application that exposes the canonical
[Haberdasher][] Twirp service over HTTP. It's the reference for everything in
the parent [`dropwizard-twirp`](../README.md) repo: server-side wiring,
client-side codegen, error semantics, and the `twirp-generate` command.

If you've never seen Twirp before, the parent README has a short
["What is Twirp?"](../README.md#what-is-twirp) intro — read that first.

## What's in here

```
src/main/proto/haberdasher.proto         # the schema (one RPC, two messages)
src/main/java/.../ExampleApplication.java # bootstrap, bundle, command registration
src/main/java/.../HaberdasherImpl.java   # business logic (server side)
src/main/java/.../MakeHatCommand.java    # CLI client demo (client side)
src/main/resources/example.yml           # dropwizard config (empty + connectors)
src/test/java/.../GeneratedClientIntegrationTest.java  # client-vs-real-server tests
src/test/java/.../ExampleApplicationIntegrationTest.java  # raw HTTP/curl tests
src/test/java/.../MakeHatCommandTest.java  # exercises the CLI demo
```

The protobuf in `src/main/proto/haberdasher.proto` is the input. Everything
under `target/generated-sources/protobuf/java/io/dropwizard/twirp/example/haberdasher/`
is regenerated by `mvn compile`:

| Generated file                | Role                                                                  |
| ----------------------------- | --------------------------------------------------------------------- |
| `Hat.java`, `Size.java`, …    | protoc's built-in Java message classes.                               |
| `Haberdasher.java`            | The service interface. `HaberdasherImpl` implements this.             |
| `HaberdasherResource.java`    | JAX-RS resource. Registered by `ExampleApplication.run()`.            |
| `HaberdasherClient.java`      | Jersey client stub implementing `Haberdasher`. Used by `MakeHatCommand`. |

## Running it

```bash
# From the repo root.
$ mvn -pl dropwizard-twirp-example -am install -DskipTests
$ cd dropwizard-twirp-example
```

### 1. Start the server

```bash
$ java -jar target/dropwizard-twirp-example-*.jar server src/main/resources/example.yml
# listens on http://localhost:8080 (app) + http://localhost:8081 (admin)
```

Or via Maven during development:

```bash
$ mvn exec:java -Dexec.mainClass=io.dropwizard.twirp.example.ExampleApplication \
                -Dexec.args="server src/main/resources/example.yml"
```

### 2. Call it with the bundled client command

`make-hat` is a Dropwizard `Command` that builds a Jersey client, constructs
the generated `HaberdasherClient`, and invokes `MakeHat`:

```bash
# Defaults: --url http://localhost:8080 --inches 12.
$ java -jar target/dropwizard-twirp-example-*.jar make-hat
12" blue fedora

# Pick a different size.
$ java -jar target/dropwizard-twirp-example-*.jar make-hat --inches 7
7" red bowler

# Use the JSON wire format instead of protobuf.
$ java -jar target/dropwizard-twirp-example-*.jar make-hat --inches 12 --json
12" green fedora

# Trip the server-side precondition to see structured error handling.
$ java -jar target/dropwizard-twirp-example-*.jar make-hat --inches 0
RPC failed: INVALID_ARGUMENT - inches must be > 0
  meta: {argument=inches}
```

[`MakeHatCommand`](src/main/java/io/dropwizard/twirp/example/MakeHatCommand.java)
is ~50 lines and heavily commented. It's the most direct way to learn how to
use the generated client from your own code.

### 3. Call it with curl (both wire formats from the same endpoint)

A Twirp service speaks **two interchangeable wire formats** on the same
URL: `application/protobuf` and `application/json`. The generated
resource declares both in `@Consumes`/`@Produces`, and `TwirpBundle`
registers a message-body reader/writer for each. The client picks the
format via `Content-Type`; the server echoes that choice in its
response `Content-Type` (per Twirp v7 — no `Accept` header required).

**JSON in, JSON out:**

```bash
$ curl -s -H 'Content-Type: application/json' \
       -d '{"inches": 12}' \
       http://localhost:8080/twirp/twitch.twirp.example.haberdasher.Haberdasher/MakeHat
{
  "inches": 12,
  "color": "blue",
  "style_name": "fedora"
}
```

**Protobuf in, protobuf out — same URL, same JVM, same resource instance:**

```bash
$ python -c 'import sys; sys.stdout.buffer.write(b"\x08\x0c")' \
  | curl -s --data-binary @- \
         -H 'Content-Type: application/protobuf' \
         http://localhost:8080/twirp/twitch.twirp.example.haberdasher.Haberdasher/MakeHat \
  | xxd
00000000: 080c 1203 7265 641a 0666 6564 6f72 61    ....red..fedora
```

(`\x08\x0c` is a serialized `Size{inches=12}` — protobuf field 1 (varint),
value 12. The response is a `Hat` with `inches=12`, a random color, and
`style_name=fedora`; the color string in your shell's hex output will
vary across requests.)

Note the URL shape: `/twirp/<proto-package>.<ServiceName>/<RpcName>`.
That's the Twirp v7 routing spec — every Twirp service uses it,
regardless of wire format.

The `bothWireFormatsCoexistOnTheSameResource` test in
[`ExampleApplicationIntegrationTest`](src/test/java/io/dropwizard/twirp/example/ExampleApplicationIntegrationTest.java)
interleaves JSON → protobuf → JSON against the same listener to prove
this isn't an accident. The generated Java client supports both too:
the default constructor uses protobuf, the `(WebTarget, String contentType)`
overload uses JSON — `MakeHatCommand`'s `--json` flag exercises that path.

### 4. Trigger a server-side error

Same endpoint, deliberate bad input:

```bash
$ curl -i -H 'Content-Type: application/json' \
       -d '{"inches": -1}' \
       http://localhost:8080/twirp/twitch.twirp.example.haberdasher.Haberdasher/MakeHat
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "code": "invalid_argument",
  "msg": "inches must be > 0",
  "meta": {"argument": "inches"}
}
```

Twirp errors are *always* JSON regardless of the request content type. That's
the spec, and it's what lets thin clients decode errors without protobuf
descriptors.

## Regenerating stubs from the packaged jar

The same fat jar also ships the `twirp-generate` command from
`dropwizard-twirp-protoc`, so once it's built you don't need Maven to regen:

```bash
$ java -jar target/dropwizard-twirp-example-*.jar twirp-generate \
       -I src/main/proto \
       --proto haberdasher.proto \
       -o /tmp/twirp-out
Wrote 3 file(s) to /tmp/twirp-out
$ ls /tmp/twirp-out/io/dropwizard/twirp/example/haberdasher/
Haberdasher.java
HaberdasherClient.java
HaberdasherResource.java
```

See the top-level [README's `twirp-generate` section](../README.md#generating-from-a-packaged-jar-twirp-generate-command)
for the full flag table.

## Tests

```bash
$ mvn -pl dropwizard-twirp-example test
```

Three suites:

| Suite                                      | What it covers                                                       |
| ------------------------------------------ | -------------------------------------------------------------------- |
| `ExampleApplicationIntegrationTest`        | Raw HTTP roundtrips — protobuf and JSON, success and error envelopes. |
| `GeneratedClientIntegrationTest`           | The generated `HaberdasherClient` against the live server.            |
| `MakeHatCommandTest`                       | The CLI demo — keeps the docs above honest.                          |

[Haberdasher]: https://github.com/twitchtv/twirp/blob/main/example/service.proto
